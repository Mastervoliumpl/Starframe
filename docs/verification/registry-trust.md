# Website registry trust

The #84 verifier is implemented on draft PR #78 against original website contract revision `fcd81be6667e2595166698178d5f55074c5ee92a`. #86 extends full signed releases to schema 2 against website #101's merged revision `1d616d43d90227ee9967091be039e6c3e695091e`; keysets and security snapshots stay at schema 1. The Rust slice accepts a registry root public key supplied outside the API and verifies a root-signed delegated keyset. It checks canonical padded base64, the SHA-256 key IDs, Ed25519, closed keyset fields, duplicate JSON keys, safe integers and the one-year validity window. Canonical JSON follows [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) for the contract's safe-integer subset, including UTF-16 property ordering.

Four website-reference signed Code, Map and AI declarations pass Rust verification. Tests reject a validly signed missing/null plan, unsupported release or installation version, schema 1 carrying a plan, and an unsigned replacement declaration. All 41 registry test entries passed locally on 26 September with isolated Windows credential access; Rustfmt and all-target Clippy passed. The sandbox's denied credential writes were rerun with the existing fixture-only permission scope.

The owner identified the existing signing backup as a possible root source. Its public catalog root uses RSA/TUF, while registry v1 requires a separate 32-byte Ed25519 root. It cannot supply this registry trust anchor. No private key or Steam credential was read. Production registry access remains unavailable; this prerequisite does not block fixture implementation or local milestone acceptance.

Signed dependency constraints now receive structural and SemVer interval validation. Validly re-signed self-dependencies, duplicate targets, missing bounds and empty/reversed intervals fail. The in-flight identity binds the dependency set as well as installation intent. Website-reference comparisons and native exact ordering are recorded in [dependency verification](registry-dependencies.md); collection/UI wiring remains open.

The synthetic keyset, security snapshot, approved release and blocked release in `tests/fixtures/registry-keys-v1.json` were signed and verified by the website's `src/lib/registry-crypto.ts` reference. All four envelopes passed the pinned website schema from `fcd81be6667e2595166698178d5f55074c5ee92a`; Rust verifies their signatures and canonical payloads. The generator and pinned schema copy stay in ignored local test evidence. Fixed synthetic seeds in Rust tests are test data, not production credentials. The tracked JSON fixture contains only synthetic public keys and signatures. Tampering, a wrong root, duplicate decoded fields and expiry fail. The application updater and old catalog keys were not used.

The delegated verifier checks security snapshots and retains each hash decision through omissions. Only a newer signed `cleared` decision removes a block. SQLite schema 16 stores signed key and security envelopes, the highest accepted revision and canonical payload for each stream, and individual hash decisions. An isolated restart test proves a block survives an empty newer snapshot and rejects rollback and a different valid payload at the same revision; it later accepts an explicit clear. This is registry trust data, separate from authentication and the old catalog cache.

A direct per-hash lookup reads retained blocks without requiring a session or fresh network metadata. The new-download gate uses that lookup after it verifies fresh signed metadata. The existing package queue and library commit, enable, and activation paths also reject a known blocked hash. A signed fixture checks that a cached release cannot start preparation, that a previously enabled mod cannot launch, that re-enabling fails after a block, and that an explicit newer clear restores access after restart. No network or session is needed for those offline decisions.

An isolated rotation test accepts a root-signed overlapping keyset, then rejects the retired key after a higher root-signed keyset removes it. No test key is provisioned as a production root.

The release verifier checks a fresh security snapshot at the exact revision named by the manifest, the requested ModID and ReleaseID, the signed archive hash and byte count, and approved metadata. Schema 16 keeps a separate revision floor and canonical payload for each release. A signed manifest block is retained by hash even if the release is unavailable. No independent production registry root has been provisioned, so the desktop refuses production registry downloads with an explicit unavailable result. #86 must use the shared hash gate when it adds new-format package installation; the old catalog path is removed under #89.

The native HTTP client now fetches keysets, security snapshots and exact release manifests from the authenticated website routes. The same bounded JSON reader rejects redirects and duplicate keys before handing an envelope to the verifier. A loopback fixture checks each route and bearer placement. No website credential or live endpoint was used.

Before a new registry grant, storage rereads the saved signatures with the independently supplied root, requires fresh matching security and release revisions, and checks retained hash decisions. The grant request uses only that verified release identity; the client rejects a returned grant with another reference, size, revision, content path or invalid expiry. This boundary has isolated restart and loopback tests. The shared desktop Downloads queue and durable receipt retry now use this boundary under #85. No production archive or live website credential was used.
