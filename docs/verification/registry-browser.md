# Native Mods browser

The discovery and detail contract pins the read-only website revision `1d616d43d90227ee9967091be039e6c3e695091e`. The list, discovery options, mod detail and release-history endpoints follow that revision's `contracts/v1/schema.json`, `src/lib/server/discovery.ts` and native browser reference in `src/routes/mods`. Installation still requires installation schema 1 inside signed full release schema 2; the unsigned listing and `modType` do not authorize file placement.

The existing Svelte shell now names the discovery page Mods. My mods remains the starting page. Rows are the default; cards and tiles use the website's page-size choices. Search, sort, periods, maintenance, type, included/excluded tags and tested builds are sent to the bounded Rust client. Paging is below results. The native response types generate the TypeScript wire contract. Discovery validates bounded options and history, identities, duplicate entries, descending publication order, security/availability pairs and page sizes. The client encodes query parameters separately from paths.

Details show the author, description, source action, artwork, maintenance/replacement information, release notes, tested build, dependency constraints, installed versions and availability. Descriptions and notes render as text. Only canonical media IDs produce URLs on the fixed official API host. The CSP permits images from that host while retaining `frame-src 'none'`; API credentials stay in Rust. The source action uses the existing backend opener after fetching and validating the mod's GitHub source URL. It grants no general frontend opener permission.

Release history selects an explicit release. Install sends its exact ModID, ReleaseID and hash to Rust. Fresh signed approval must still match that triple before the existing authenticated package queue starts. Queue acceptance is shown separately from confirmed installation. An installed version does not cause automatic replacement, enabling or collection edits. Different tested builds produce a warning. Missing installation information, unavailable releases and confirmed blocks explain their unavailable action.

Sign-in triggers discovery after the shell is usable. Checks recur every five minutes while Starframe stays open, including another page; they do not overlap an active list read. Manual refresh keeps query, selection and focus. Navigation retains component state. Detail Back restores the list's focus and scroll; windows below 1280 use the full workspace detail. Stale list/detail replies and responses from a retired account are discarded. A scoped network failure retains previous results in memory and identifies them as previous results. Installed/local persistence is unchanged. Signing out clears account-scoped discovery without disabling ordinary installed/local management.

## Combined native registry acceptance

The isolated native API fixture now runs discovery, options, detail, history, exact signed approval, download, receipt and library commit through the real Tauri commands and shared worker. It independently supplies an ephemeral Ed25519 fixture root and protected synthetic session in a temporary debug data directory. The configuration accepts only a matching HTTP loopback origin; release builds omit this mechanism and retain the fixed production connection and unprovisioned root gate. The one-use credential seed is consumed after Windows protected storage accepts it. No private signing key or bearer token crosses the frontend boundary.

The fixture explicitly selects and installs an older release, then the newest release, retaining both exact references without enabling or replacing collection entries. Tampered and expired signed release metadata fail before a new download grant. A restricted response leaves Collections and the installed library available. API outage on reopening preserves both releases and allows selecting the older one. A later 401 reopening removes the synthetic session while preserving the library, selection, Settings and local import controls. Receipt claims reach the fixture API once per release. The native capture at 1280 × 800 confirms the established shell, readable release details and installed state; raw captures remain ignored under `test-results/native`.

The first native run exposed missing Tauri permissions for authentication and receipt/download commands after the explicit command manifest was introduced. Those commands now have generated allow permissions in the main-window capability. The combined fixture verifies the corrected boundary. Two later failures were fixture locators that did not match the current UI; correcting them required no product change. The Windows fixture needs credential-vault access outside the restricted shell sandbox. This is synthetic acceptance; it does not establish hosted Steam or production trust readiness.

For this increment, frontend formatting/lint/types, 17 Vitest tests, production build, Rustfmt/Clippy and the full Rust gate passed (171 library tests, 12 executable tests and the configuration/headless/runtime-contract suites). The embedded debug build and all eleven native cases passed across the initial suite and the focused remainder. The cleanup case initially read the previous installation’s ready text before the new fixture loader existed; it now waits for that second loader, and cleanup/updater passed on rerun. No maintenance behavior changed. Repository checks passed. Browser, C#, installer and real-game evidence are reused because those implementations did not change. Hosted checks for the new commit are required separately.
