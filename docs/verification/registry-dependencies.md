# Registry dependency resolution

The backend dependency rules use website revision `1d616d43d90227ee9967091be039e6c3e695091e`, `contracts/v1/README.md` and `src/lib/server/author-input.ts`. A release has one dependency per other ModID. Exact constraints bind both ModID and ReleaseID. Ranges are half-open SemVer intervals: inclusive `minimum`, exclusive `before`, at least one bound, and explicit prerelease participation. Build metadata does not change precedence; ordinary version labels require exact constraints.

Signed release validation now rejects self-dependencies, duplicate targets, invalid or empty ranges, missing nullable bound fields, invalid exact UUIDs and dependency problems that do not describe the release's declared constraints. Installed metadata uses the same checks. The original in-flight download/install identity also binds the approved dependency set. A higher signed manifest that changes dependencies at the same metadata revision cannot pass the original identity check; existing installed approvals remain unchanged.

The existing Rust SemVer crate represents core numbers as `u64`; the website accepts arbitrary-length numbers within its 100-character version limit. A small internal parser implements that bounded grammar and compares decimal numbers by length and digits. It introduces no dependency or expression language. Website-generated fixtures cover nine constraints, 180 candidate comparisons and eleven structural rejections, including numbers larger than `u64`, build metadata, prerelease ordering and non-SemVer labels.

Candidate suggestions filter unavailable or blocked discovery records and prefer the newest publication satisfying the constraint. They return an exact reference for explicit selection, not signed download authority. The existing fresh signed approval, security, grant and final install checks remain required before installing it.

`ordering::resolve_registry` resolves an explicitly selected set against installed exact references. It reports missing entries, disabled dependencies, incompatible selections and cycles. It never chooses replacement bytes or enables a dependency. Dependencies come first; unrelated priorities use the existing stable topological ordering and cycle detector. Synthetic tests retain distinct UUID approvals with the same version text and archive hash, reject substituting either approval, check range/prerelease conflicts and verify reported order adjustments. Existing local ordering tests pass after extracting the shared algorithm.

The combined reference type has closed `kind` and `reference` fields. Registry references retain the exact numeric ModID/UUID ReleaseID/hash triple. Local references retain the declared string ID and managed content hash. Neither accepts URLs, credentials or a catalog origin. The adapter from existing local records explicitly rejects catalog references; it does not translate old IDs.

`ordering::resolve_mixed` now merges registry dependency edges and existing local dependency/ordering constraints into the same stable graph. Manual interleaving survives unless required edges constrain it. Duplicate selected versions, exact-reference conflicts, missing local builds, cycles and conflicting runtime settings keys fail. Local optional preferences remain advisory. Registry and local metadata do not authorize each other's identities.

`backend::prepare_references` and the internal `setup-selection` command use the combined order and activation builder. The local builder and streamed payload owner are extracted from existing code. New selections include both origins, preserve existing local runtime/settings IDs, deploy Code and Map/AI through one journal, and retain bounded disabled Code inventory. Fresh online sessions are unnecessary for installed reuse; retained blocks and source verification remain required. Fixtures cover manual interleaving, required/optional constraints, missing and changed exact approvals, duplicate IDs, catalog-dependency rejection, local/registry key conflicts, local imports through the existing queue, offline reopening, changed copied-file retention and a 260-entry display library with a 256-entry runtime inventory and four omitted disabled entries. The full isolated setup fixture now includes a local import and disabled local build alongside all four registry formats.

Persisted collections now use the combined references, through the ordinary desktop/backend owner. Membership, reorder, select, rename, delete and uninstall preserve those references. A registry dependency must already be explicitly selected; a local exact dependency retains its existing automatic enable behavior. Reordering changes priority without choosing another release. Shared collection schema 2 accepts only closed exact registry/local references and an ordered list, without settings, URLs or paths. Existing installed entries verify through the shared three-worker queue without a session or fresh online metadata. Corruption and retained security blocks remain unresolved, and interrupted work needs explicit retry. Export retains the exact original references and order.

SQLite schema 19 backs up the database before discarding obsolete pre-release collection/import records and replacing their tables. This follows the owner's waiver; it adds no ID mapping or old collection reader. Local library copies, original source files, watched-source metadata, settings and deployment journals remain. Native reference keys, contiguous order and closed import records are checked during load/backup/restore. Rebuilds update only matching entries in active locally created collections; shared and inactive collections retain their exact builds. Content-only registry files are excluded from the Code runtime byte limit during rebuilds.

The existing Svelte My mods, Collections, sharing and keyboard/drag ordering controls consume the combined wire type.
