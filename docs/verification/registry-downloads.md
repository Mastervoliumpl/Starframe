# Registry downloads

Issue #85 is in progress against the committed website delivery contract `fcd81be6667e2595166698178d5f55074c5ee92a`. The website checkout is read-only to this task; its current #101 edits are unfinished and were not used to define this transfer.

The storage boundary derives a download identity only from saved, fresh signatures for the requested ModID and ReleaseID. It checks the retained hash decisions before returning the exact hash, size, approved metadata revision and security revision. The authenticated grant request sends those values. The response must repeat them, carry a relative content path for its DownloadID and have a short valid expiry. A 2 GiB archive cap matches the website upload limit.

The content reader uses a separate HTTP client without the JSON request's 30-second total timeout. It streams into a caller-owned staging file. It accepts only the website SHA-256 ETag, explicit size and range headers, a complete 200 response or a matching 206 suffix. A 200 response resets a partial file. A 416 remains a distinct error for the caller to handle. Completion reads the whole staged file in bounded chunks and checks the signed SHA-256 before returning success. A corrupt or partial file receives no success result.

The content reader returns a verified-archive value only after the complete hash check. The receipt method requires that value and the same active manager account that received the grant. It sends the DownloadID, hash and byte count, and checks the receipt's ReleaseID. Schema 17 saves a receipt claim only from that verified result. A pending claim survives restart and can be retried by the same account without a new grant or archive transfer; a failed acknowledgement retains it, and a confirmed response clears it. A duplicate server response with `counted: false` is valid. The claim records the archive transfer, not installation; local cache reuse creates no claim. Loopback tests check the durable retry after a simulated 503, a different account's empty pending list, receipt identity and duplicate acknowledgement.

A bounded same-session helper renews a grant after a broken transfer and attempts the locally saved prefix with the same verified identity and account. The website records only a fully delivered requested range, so a new grant may reject a local partial prefix with 409. The helper then truncates the staging file and retries from byte zero under that grant. Loopback tests cover a fresh transfer, interrupted transfer followed by grant renewal and 409 restart, a suffix resume after an acknowledged prefix, a full restart of a partial file, changed bytes, 416, cancellation and rejection after an account change. A 32 MiB fixture sends fixed 64 KiB chunks and checks the final file size and progress without constructing the archive in memory. The grant fixture checks the exact identity and rejects an external content URL. No website credential, live archive, real game or installer was used.

The helper starts with an empty staging file, so it does not resume a previous process's unbound bytes. A storage recheck compares the original exact identity with the current fresh signed release and security state after transfer; a newer signed block or changed approval stops promotion. A loopback test covers a renewed grant that accepts the saved prefix with a 206 suffix.

The client has a completion check against `GET /v1/session`. It requires the same account and a current manager download capability; a loopback fixture rejects a changed account or removed capability. The shared Packages queue now uses that check before saving a registry archive. It applies the existing three-operation limit and free-space check, reports progress and accepts cancellation. The queue records a receipt claim only after a full verified transfer. It then rechecks the signed release and security state, verifies the staged archive again and saves it by exact hash. The archive remains separate from the mod library until #86 supplies a signed installation plan. A cached archive is rehashed before reuse and produces no new grant or receipt.

An isolated queue fixture uses fresh synthetic signatures and loopback grant, content, session and receipt endpoints. It confirms a saved exact archive and receipt without a library entry, then reopens storage and reuses the cache without network access. A second fixture makes the receipt return 503, restarts storage and sends an account-bound duplicate acknowledgement. The claim survives the 503 and clears after the retry; no archive is transferred again. Rustfmt, Clippy and the full Rust suite passed for this increment.

Before a new registry request, the queue removes abandoned UUID-named staging files and leaves active stages and unrelated files alone. Failed or cancelled transfers remove their partial staging file after the worker stops; a cleanup failure is reported on that operation. An isolated recovery fixture checks this ownership boundary. A stalled loopback transfer cancelled through the queue ends as cancelled, removes its partial file and creates no receipt claim. A previous process's partial bytes are not resumed under a new grant.

Two queue fixtures stop promotion after a complete transfer: one accepts a newer signed block before queue completion; the other changes the authenticated account at the final session check. Both retain the original account's receipt claim, remove staging, save no archive and create no library entry. All six registry queue fixtures, Rustfmt and Clippy pass on this increment.

The desktop `registry_download` command now validates ModID, ReleaseID and request UUID, passes the authenticated account to the storage worker and starts the shared queue. Its production trust root remains unset because no independent registry root has been provisioned. The command returns `registry_trust_unavailable` before requesting a grant; local mods remain usable. A test checks that boundary. The Downloads view labels a completed registry transfer `Archive saved` and does not offer the old catalog retry action for it. Saved operations from earlier builds default to the existing package kind. No production download or registry installation has occurred.

The desktop can retry pending download receipts through the signed-in account without requesting another archive. Each verified transfer saves its receipt claim and operation link in one storage transaction. A completed acknowledgement clears both in one transaction; a failed retry leaves both pending and reports the result on a saved archive operation. The restart fixture checks that a duplicate server acknowledgement clears the saved pending label without another content request. Downloads shows a retry action only when an operation has a pending receipt, and explains the account requirement. The registry browser entry point remains for #85.

Cached-archive checks and the final pre-promotion hash now run on download workers. The storage worker can continue servicing unrelated desktop requests while a large archive is hashed. Cancellation is checked during each hash pass, and account cancellation is checked before cache reuse or promotion. The queue fixture checks that a changed cached archive fails without a new grant or receipt. Archive promotion still requires the same signed release and security state checked after transfer. Production registry downloads remain unavailable until a separate registry root is provisioned.
